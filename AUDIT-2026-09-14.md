# WorkReady audit

Date: 14 September 2026

## Summary

WorkReady has a substantial educational simulation and a sensible starting point for pseudonymous participation. It is not yet ready for an unsupervised cohort using real personal material. The most urgent issues are unauthenticated transcript access, incomplete credential protection, incomplete deletion, and overstated privacy claims.

Earlier assurances that all ownership checks were complete, that sign-out fully cleared the session, and that imported contact details could never leave the server were incorrect. The findings below replace those assurances.

This review made no application changes and no changes to the live service. This report is the only added workspace file.

## Scope and verification

Reviewed the API, student portal, job board, company-site templates and application script, primer, local publishing console, lecturer dashboard, and deployment configuration.

Verification included:

- Isolated FastAPI tests with a fresh temporary SQLite database, fictional users, and synthetic transcripts. No real student transcripts were requested from production.
- Stub-mode processing and mocked LLM calls to inspect what would reach an assessor without sending personal material to a provider.
- Isolated JavaScript execution to reproduce a late login response after sign-out and the individual build-button failure.
- Read-only public health, OpenAPI, admin-page, static JavaScript, and CORS checks.
- Read-only Docker inspection of runtime provider, storage configuration, and log configuration. No secret values were printed.
- GitHub Actions status checks. Recent portal and deploy workflows were successful.

The API returned HTTP 200 from `/health`. The deployed API uses `LLM_PROVIDER=stub`. The public portal's `/admin.html` returned HTTP 404, and unauthenticated admin API access returned HTTP 401.

No concurrency/load test or complete real-browser, mobile, accessibility, or external hiring-desk conversation audit was performed. Recent Docker log retrieval timed out, so current log contents were not reviewed. The separate AnythingLLM provider, retention settings, and model configuration remain unverified.

## Privacy and security findings

### P0. Transcript routes bypass ownership checks

Confirmed in isolated tests. Requests without any code returned HTTP 200 and the synthetic private transcript from:

- `GET /api/v1/interview/{session_id}`
- `GET /api/v1/exit/application/{application_id}`
- `GET /api/v1/perf-review/application/{application_id}`

The public OpenAPI definitions match these unauthenticated signatures. The general interview-session route does not restrict the session kind either.

Additional unguarded routes include calendar listing and accept/decline actions, single lunchroom-session lookup, interview slot listing, and marking messages read. Tests confirmed that anonymous requests could read a synthetic calendar, accept an event, and mark another user's message read.

Some controls work: a non-owner received HTTP 404 from the guarded application-detail route. The problem is incomplete coverage, not the absence of all protection.

Fix: use a common authenticated-student dependency and object-ownership resolver for every private read and write. Create a route-by-route test matrix for anonymous callers, the owner, another student, and revoked credentials. Check session kind as well as ownership.

Evidence: `workready-api/workready_api/app.py:2227`, `:2425`, `:2611`, `:896`, `:2992`, `:3020`, `:3038`, `:3111`, `:1494`.

### P1. Credentials travel in URLs; revocation is incomplete

The contractor code is a reusable login secret. It is placed in API path parameters, query parameters, and the portal-to-job-board URL. This exposes it to request logging and, for navigation URLs, history, copied links, and hosting access logs. Removing the query string with `history.replaceState` does not undo the original request.

The initial mailbox local part is also derived directly from the code, before a persona is set. Keep public-facing identifiers separate from credentials.

`GET /api/v1/student/{code}` uses `get_student_by_code`, not the active-code resolver. In a test, the progress endpoint returned HTTP 200 after code revocation while the state endpoint rejected the code.

Fix: exchange the issued code for a separate, expiring session through a POST login. Use a secure HttpOnly cookie where the deployment supports it, or a short-lived bearer session, with a revocation check. Stop sending the original code in URLs. Redact credential-bearing paths/query values from logs and rotate exposed demo credentials before reuse.

Evidence: `workready-portal/app.js:131`, `:313`, `workready-jobs/src/app.js:575`, `workready-api/workready_api/app.py:697`, `workready-api/workready_api/db.py:405`.

### P1. “No PII” and “nothing leaves the server” are not accurate

Access codes reduce the need to collect identifying registration details. They do not make all saved content anonymous.

The system stores a display name, conversation transcripts, messages, task bodies, feedback, and task attachment text. A student can supply a real name or disclose personal circumstances in any of those fields. A name being self-declared does not make it fictional.

The resume redactor removes matching email addresses, Australian phone numbers, some links, and explicitly labelled address lines. A synthetic test retained a full name, unlabelled street address, date of birth, passport-style identifier, and non-Australian phone number. It is a useful filter, not an anonymisation guarantee.

Other input paths are not equivalently filtered. A test confirmed that the cover letter reaches the assessor unchanged. Task attachments are extracted without this redaction. Cloud-model implementations send prompts and transcripts to Anthropic/OpenRouter when selected. Ollama may also be remote, depending on its URL.

The currently deployed API is in stub mode, so those main API cloud-model calls are not active today. The hiring-desk widgets are a separate service and require a separate data-flow review.

Fix:

- Describe the product as **pseudonymous participation with fictional profiles and data minimisation**.
- Default to supplied synthetic resumes and explicitly ask students to choose an invented persona name.
- For real uploads, provide a sanitised preview before submission and explain the filter's limits.
- Apply consistent handling to cover letters, messages, task attachments, and model prompts.
- Publish a short notice explaining what is saved, who can read it, the active AI provider, retention, deletion, and that AI output is educational feedback.
- Correct the portal's “nothing here identifies you” wording and equivalent deck/documentation claims.

Evidence: `workready-api/workready_api/pdf.py:16-49`, `app.py:491-505`, `:2746-2807`, `interview.py:194-251`, `db.py:52-59`, `:103-160`, `:197-207`; `workready-portal/index.html:422-427`.

### P1. Student deletion fails for established placements

Both admin reset and delete returned HTTP 500 when the synthetic student had a dependent task. The deletion code removes applications without removing all dependent tables. Tasks, submissions, calendars, lunchroom data, and message attachments are not included in its deletion sequence. Foreign keys do not supply cascading deletes for those relationships.

Deleting a mailbox message is a soft delete. That is not a retention policy or a complete erasure mechanism.

Fix: implement a transactional deletion plan covering every student-related table, attachment files, derived summaries, and backups. Test it with a completed placement, uploaded attachment, lunchroom conversation, and coaching session. Define a cohort retention period and a backup expiry policy.

Evidence: `workready-api/workready_api/admin.py:310-368`, `db.py:153-265`, `mail.py:573-587`.

### P1. Attachment storage is outside the durable volume

`Path("")` evaluates to a truthy Path object, so the fallback in `ATTACHMENTS_DIR = Path(env_value) or db_parent / "attachments"` never activates when the variable is unset.

Live inspection confirmed:

- Attachment directory resolves to `/opt/workready/workready-api`.
- The persistent mount is `/opt/workready/data`.
- `WORKREADY_ATTACHMENTS_DIR` is not configured.

Mail PDFs therefore remain raw in the container filesystem, outside the intended persistent directory. Container replacement can lose them while the database keeps their metadata. Reusing the same filename also overwrites the previous file for that student.

Fix: explicitly configure an attachment directory inside the data volume, use generated storage filenames, retain original names only as metadata, validate file type/size, and include the files in deletion and backup procedures. Decide whether retaining original resume PDFs is necessary at all.

Evidence: `workready-api/workready_api/mail.py:47-51`, `:245-258`, live mount/configuration inspection.

### P1. The limiter changes error status but does not stop authentication work

After ten failed requests, the state route returns HTTP 429. However, each attempt still reaches credential lookup, and a valid code still succeeds immediately after the threshold. The profile route has no limiting logic. Other code-validation routes bypass it too.

More importantly, `/resume` extracts and assesses the PDF before validating the code or checking the placement-attempt cap. A mocked test confirmed an assessor invocation for an invalid code even when the response was HTTP 429. With a paid provider, unauthenticated requests could consume model calls. Resume/task upload paths also lack a clear server-side size cap before reading the full upload; mail checks its 5 MB limit only after reading the entire file.

Fix: authenticate and enforce quotas before expensive processing. Enforce a real cooldown or request budget before validation, return `Retry-After`, rate-limit all authentication paths, and cap upload/body sizes at the proxy and application. Configure trusted proxy handling so a per-IP limiter uses the intended client IP.

Evidence: `workready-api/workready_api/app.py:407-422`, `:491-536`, `:761-783`, `:846-869`; `mail.py:245-249`.

### P1. A late response can undo sign-out

An isolated JavaScript test started `signIn()`, called `signOut()`, then delivered the old successful login response. The callback restored the credential to localStorage and reactivated state.

Polling responses also lack a request/session generation check. Sign-out does not clear all Teams, exit, coaching, mail and rendered DOM state. Hiding the app alone is not sufficient for shared-device account switching.

The error overlay intercepts pointer clicks but has no focus trap or `inert` background. Keyboard users can still navigate background controls.

Fix: cancel in-flight requests and invalidate callbacks with a session generation counter. Clear all user-specific state and DOM at sign-out. Make the modal an accessible dialog with focused actions, trapped focus, and an inert background. Use a shared-device mode that does not persist credentials.

Evidence: `workready-portal/app.js:131-171`, `:190-204`, `:222-250`.

### P1. The local console needs stronger boundaries before delegation

Loopback binding is useful but is not authentication against hostile browser content. With the default empty `CONSOLE_TOKEN`, an isolated test showed that a cross-origin simple POST reached the build handler. The subprocess was mocked, so no build or deploy ran during the test. The console also accepts arbitrary Host headers. This permits unwanted browser-triggered operations and leaves a DNS-rebinding risk.

Its optional token mode is not wired through the UI: loading `/?token=...` succeeds, but subsequent `fetch('/api/files')` calls do not forward the token and receive HTTP 401.

The publish handler runs `git add -A` on every dirty repository, including API and deploy repositories. It can publish unrelated edits or accidentally added data, not just the selected content. It has no selected-file deployment plan, concurrency lock, build/test prerequisite, or partial-push recovery. A clean repository with an unpushed commit is skipped.

Fix: require a local authenticated session, validate Host and Origin, require anti-CSRF protection for mutations, serve previews on a separate origin, and remove privileged credentials from browser-readable storage where practical. Publish only reviewed files in an explicit deployment plan. Run builds and checks first, serialise operations, and handle partial failures visibly.

Evidence: `workready-deploy/console/app.py:56-69`, `:171-240`; `console/static/index.html:98-103`.

### P2. Third-party script and hiring-desk boundary

Company templates embed an external AnythingLLM JavaScript widget in the same page as application forms. A script loaded this way executes with the page's privileges; its configuration and supply-chain trust matter. No exfiltration by the widget was tested or observed.

Fix: isolate the hiring desk in a separately hosted iframe where practical, restrict external script/connect sources, document its provider and retention separately, and keep contractor credentials out of any bot input. Use owned or reserved domains for fictional addresses so they cannot be confused with real delivery destinations.

Evidence: `nexuspoint-systems/site/templates/base.html.j2:85-91`; corresponding pattern exists in the company sites.

## Strengths to keep

- Random issued codes and an externally held roster mapping are a useful data-minimisation foundation.
- Admin API routes share a token-check dependency and constant-time comparison. The live public admin page is removed.
- Many application, task, and chat routes do enforce ownership correctly.
- Core simulations can run in stub mode without external model calls. The deployed API currently does so.
- Most student message/transcript rendering uses textContent or escaping. Preserve that pattern as features grow.
- The story, fictional company sites, personal/work inbox split, coaching, and lecturer reports give the simulation a coherent educational structure.
- Static content and application code are versioned. SQLite persistence is mounted separately from the container image.

## Suggested privacy-first product design

1. Separate identity layers. Keep the issued code private as an enrolment credential, use a separate session for requests, and show only the chosen fictional persona in the simulation.
2. Put a brief notice before profile/upload/chat. Explain saved data, lecturer visibility, AI provider, synthetic material preference, and retention. Avoid promising that arbitrary user input cannot identify anyone.
3. Make synthetic mode the default. Provide clean, plausible sample resumes rather than keyword-token lists. Allow real-material mode only with a deliberate, reviewed handling policy and sanitised preview.
4. Give lecturers scoped access. Keep management local if preferred, but retain server-side authorisation. Before delegation, add named accounts, cohort scope, and a minimal audit trail for administrative actions.
5. Make deletion verifiable. Include attachments and derived records, define backup expiry, and show an erasure result rather than only a success message.
6. Make the active mode visible to staff. Show stub/local/cloud provider, pacing preset, and data handling. Keyword- and length-based stub scores are not validated educational assessments.
7. Publish staged releases. Build and test against a synthetic database, pin source revisions/image digests, deploy compatible API and frontend versions, health-check, and retain a rollback target.

## Recommended work order

### First: privacy release

- Close every private-route authorisation gap and make revocation consistent.
- Stop sending reusable codes in URLs; add sessions and real pre-processing limits.
- Correct privacy promises and apply a consistent input/provider policy.
- Repair erasure and attachment storage.
- Fix logout races and harden the local console's request and deployment boundaries.

### Second: journey and console reliability

- Repair Quick Apply, company applications, lunchroom slot selection, and local admin connectivity.
- Resolve resubmission/exit/coaching sequencing and booking credential omissions.
- Fix console build controls, token forwarding, preview isolation, and selective publishing.
- Add permanent contract tests using the exact browser payloads. Existing `scripts/smoke_chat_routes.py:57-71` still omits the now-required code; earlier one-off tests that substituted titles or forced state transitions did not prove the actual browser journey.

### Third: teaching and design polish

- Pilot with synthetic profiles across two or more simultaneous users.
- Review next-action guidance, accessible dialogs, persona editing, mobile task submission, and resume formats in real browsers.
- Calibrate formative feedback with educators, show limitations of stub scoring, and add a human review path.
- Test named workshop and semester presets, then expose those in the configuration console.

## Safe description for external discussions

> WorkReady is a configurable internship simulation with pseudonymous access codes and fictional profiles. It records simulation activity for learning and lecturer review. Synthetic resumes are recommended, and matching contact details are filtered from resume assessment input. Data handling depends on the selected AI provider and deployment settings.

That statement supports the real strengths without claiming anonymity, perfect redaction, or unlimited scale.
